### Answers

- **Q1 Item 10: ComposeDigest content, label key, how each tool compares; podman write order and 'unchanged'; can a step fail after the writes and before the restart; trace B.**
  - ComposeDigest hashes len(file)+file, then each env entry sorted, NUL-separated, secret values included, variable itself absent. Label keys are per tool: A 'solace-connector/deploy-sha256' filled from env _GEN_DEPLOY_SHA256; B 'solace-util.deploy-sha256' filled from SOLACE_DEPLOY_SHA256. Compare: A reads the running container label via runner.DockerDeployDigest (list, then inspect.Decode Labels[key]) and asks when have != digest (absent label or failed inspect = changed); B deployedDigest does the same through containercli.List/inspect. Podman in A: version -> read unit file and compare -> PodmanSecretMatches per secret (4.7+; older counts all changed) -> stale list -> approve if running and changed -> write(): secret create (changed ones), secret rm stale, write unit 0644 -> daemon-reload (only if changed) -> start or restart; 'unchanged' = unit bytes equal and every stored secret equal. B: same compare, approve, writePodmanSecrets, writeArtifact (0600), removeLegacyCertBundle, daemon-reload (if changed), start/restart; unchanged = same test, then 'left running'. Yes, both can fail after the writes and before the restart (daemon-reload, restart, and in B removeLegacyCertBundle), and the re-run then reports unchanged with exit 0 while the old container runs. The B CR-0014 trace is confirmed; A has the same defect.
  - Evidence: M containercli/containercli.go:130-155; A main.go:782-811,956-1003, runner.go:733-781, defaults.go:286, dockergen.go:57-62,182; B manager.go:791-856,877-941, render.go:694-706,1175; B review CR-0014 :1554-1580
- **Q2 Item 10: digest over a unit that carries the label; how compose avoids it; does it cover secret values; where is the label readable.**
  - Compose avoids it because the file holds only a constant placeholder (label: ${VAR:-}) and the digest is taken over that file plus the env before the variable is added, so the label is never inside the hashed bytes. A quadlet has no interpolation, so the tool must render the unit without the Label= line, hash it with the secrets, then render with the line, and compare the label of the running container (never the file). The compose digest covers secret values (the env holds them). The label is readable by anyone who can run docker/podman inspect or ps --format on the container (inspect.Container.Labels, M inspect.go:47,106). On podman it is also in the unit file: A writes 0644 (main.go:993), B 0600 (manager.go:740). A unit-only digest cannot fix a rotated password, so the digest must cover secrets (see problems).
  - Evidence: M containercli.go:130-155; A dockergen.go:182, main.go:782-786; B render.go:1175, manager.go:891-892; A main.go:993; B manager.go:740
- **Q3 Item 11 in A: kubectl call sites, context read/printed/pinned, execguard and --context/--kubeconfig, destructive prompts naming cluster/context, does B's CR-0026/CR-0082 problem exist in A.**

- **[confirmed] 7. Quadlet Environment= reaches the service as ExecStart --env; $ / ${NAME} expansion vs escaping; % specifiers in Volume=, Image=, Label=, Environment=**
  - Environment=, Label= and Annotation= are mapped to '--env', '--label', '--annotation' podman args (keyValKeys in ConvertContainer) and the whole argv is written into the generated ExecStart= via AddCmdline/escapeWords. Quadlet's escaping only handles whitespace, control chars, double and single quotes and backslash (charNeedEscape); it does NOT double '$' or '%'. So systemd then treats ExecStart normally: '${FOO}' and '$FOO' are expanded by systemd (unknown variables become empty), a literal dollar must be written '$$' in the unit file; '%' specifiers (%h, %t, %n, %N, %i ...) are expanded by systemd in ExecStart command lines ('%%' for a literal percent). That applies to any value that ends up in ExecStart, including Image=, Volume=, Label=, Environment=. Quadlet itself only special-cases leading '%' in paths (does not resolve them as relative) and %N in pods; source comment: 'it is difficult to properly implement specifiers handling without consulting systemd'. The podman man page says Environment 'uses the same format as services in systemd' but has no $ or % note; the '$$' rule is documented in systemd.service and shown in podman discussion 25053 (Exec=...$${FOO}). I did not find an upstream issue stating the Environment= case specifically, so Environment= '$' behaviour is derived from source plus systemd docs. On the input side, values are split with SplitUnquote|SplitCUnescape, so a value with spaces must be quoted in the unit file.

- **[confirmed] 10. docker compose down with no such project: exit status/output; what decides project name and order**
  - Exit 0, not an error. down.go logs the warning 'No resource found to remove for project "NAME".' via logrus Warnf (stderr) and returns nil; not-found errors from loading project resources are ignored. Caveat: with explicit service names and an explicit compose file it can error on a missing service. - **[confirmed] 11. A PersistentVolume is cluster-scoped; what happens to a PV when its PVC is deleted, by reclaim policy; statically provisioned PV**
  - Scope: PVs are not in any namespace (namespaces docs list PersistentVolumes next to Nodes; the PV doc calls them cluster resources; PVCs are namespaced). Retain: when the PVC is deleted the PV object remains, phase Released, not available to another claim, the data stays, and an administrator must clean it up manually (delete the PV, scrub or delete the storage asset). Delete: for plugins that support it, the PV object and the backing storage asset are both removed; if automated reclamation fails the phase is Failed. Defaults: dynamically provisioned PVs inherit the StorageClass reclaimPolicy, which defaults to Delete; manually created (statically provisioned) PVs default to Retain per the PV API reference, so deleting the PVC leaves such a PV in Released unless an admin set Delete. The Solace operator docs say PVC and PV are kept when the broker or deployment is deleted and that deleting a PVC deletes its PV, consistent with a Delete class. Recycle is deprecated. The doc text that a Released PV keeps its old claimRef was not seen in the fetched text; 'not available for another claim' was.
